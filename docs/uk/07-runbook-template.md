# Шаблон runbook'а (і один заповнений)

Runbook пишеться для **втомленого вас о 3-й ночі**. Коротко, по порядку, з точними командами і чітким рядком «зупинись і ескалюй».
Пишіть його після кожного drill. Якщо не вдається вкластись у пів сторінки, ви ще не зрозуміли відмову.

```
# <Назва проблеми так, як її назвав би alert чи симптом>

## Симптом
Що ви бачите? (назва alert'а, повідомлення про помилку, дашборд)

## Спершу підтвердьте (30 секунд, лише читання)
1. команда  → як виглядає ПОГАНИЙ результат
2. команда  → ...

## Чому це зазвичай трапляється
Один-два рядки.

## Виправлення
1. команда            (зазначте, що вона змінює)
2. команда
Очікуйте: як ви дізнаєтесь, що спрацювало.

## НЕ робіть
- спокусливий хибний хід і чому

## Ескалюйте, коли
- ситуація, в якій ви зупиняєтесь і телефонуєте комусь

## Після
- що перевірити завтра, що покращити, щоб не повторилось
```

## Приклад: «У Postgres нема primary: записи падають» (з drills 01, 03, 04)

### Симптом
Alert `PatroniNoLeader`, або застосунок логує `connection refused` / `read-only transaction` на порту 5000. `patronictl list` не показує `Leader`.

### Спершу підтвердьте
1. `patronictl list` → **нема рядка Leader**, або всі учасники `Replica`.
2. `docker exec etcd1 etcdctl endpoint health --cluster` → **будь-який «unhealthy» / менше ніж 2 здорові.** Якщо так, це проблема *etcd*, а не Postgres: переходьте до «etcd» нижче.
3. `docker logs pg1 2>&1 | grep -E "demoting|lost|DCS" | tail -5` → `demoting self because DCS is not accessible` підтверджує.
4. `curl -s localhost:8101/patroni | jq .state` для кожного вузла → чи працює Postgres бодай на одному?

### Чому це зазвичай трапляється
(а) Primary помер або був відрізаний: чекайте до `ttl` (30 с), репліка має промотитись сама. (б) etcd втратив кворум: Patroni демотить primary **навмисно**.

### Виправлення
- **Якщо від відмови минуло менше 40 с і etcd здоровий: чекайте. Нічого не робіть.** Передчасний ручний failover — звичайна причина втрати даних.
- etcd впав: спершу відновіть etcd (`docker start etcd2 etcd3` тут; на справжніх хостах запустіть учасника й прочитайте його лог). Patroni відновиться сам протягом одного `loop_wait`.
- etcd здоровий, але лідера нема > 60 с, і репліка стрімить з lag 0: `patronictl failover --candidate pg2`. Прочитайте запит підтвердження.
- Вузол показує `start failed`: див. «репліка не стартує».

### НЕ робіть
- Не робіть `pg_ctl promote` вручну на вузлі Patroni: Patroni і Postgres розійдуться, і вийде два primary.
- Не запускайте `patronictl failover`, поки старий primary може бути живим і досяжним для клієнтів (створите split brain).
- Не перезапускайте всіх учасників etcd одночасно.

### Ескалюйте, коли
etcd втратив дані (учасники не згодні), або два вузли обидва вважають себе primary, або єдиний актуальний вузол — той, що не стартує.

### Після
`patronictl history` для timeline; еквівалент `make report` з вашого моніторингу за вікно простою; перевірте, що старий primary повернувся (`patronictl list`: усі `streaming`).
