# Бекапи та point-in-time recovery (PITR)

Реплікація — **не** бекап. `DROP TABLE` чи хибний `UPDATE` реплікується на кожну репліку за мілісекунди.
Тільки **базовий бекап плюс заархівований WAL** може повернути вас до «за секунду до помилки».

```
 базовий бекап (понеділок 02:00)     WAL-сегменти архівуються безперервно
 ┌────────────────────┐   ┌───┬───┬───┬───┬───┬───┬───┬───┬───┐
 │ копія файлів       │ + │ 1 │ 2 │ 3 │ 4 │ 5 │ 6 │ 7 │ 8 │ 9 │ ...  кожна зміна після бекапу
 └────────────────────┘   └───┴───┴───┴───┴───┴───┴───┴───┴───┘
                                          ▲
                              recovery_target_time = «просто перед DROP»
```

Відновлення = скопіювати базовий бекап, потім **програти WAL** з архіву до цільового моменту, потім зупинитись і відкрити для роботи.

## Три числа

| | Значення | У цій лабораторії |
|---|---|---|
| **RPO** (дані, які можна втратити) | час від останнього заархівованого WAL | `archive_timeout = 60` с у гіршому разі |
| **RTO** (час до повернення) | час копіювання бекапу + програвання WAL | виміряйте в drill 10, потім екстраполюйте на ваш розмір |
| **Retention** (утримання) | як далеко назад можна піти | доки ви зберігаєте бекапи **і** WAL від найстарішого з них |

## Що змушує це працювати (усе налаштовано в `patroni.yml.tpl`)

```
wal_level = replica          # достатньо WAL для реплікації і PITR
archive_mode = on
archive_command = cmp -s %p /archive/%f || { cp %p /archive/%f.tmp && mv /archive/%f.tmp /archive/%f; }
archive_timeout = 60         # закривати WAL-сегмент щонайменше раз на хвилину
restore_command = cp /archive/%f %p
```
- `%p` = шлях до файлу WAL, `%f` = його ім'я. Команда має повертати **0 лише тоді, коли файл надійно збережено.**
- Копіюйте під тимчасовим іменем і робіть `mv`, щоб відновлення ніколи не побачило недописаний файл.
- **Тестуйте команду.** Зламаний `archive_command` змушує `pg_wal` заповнити диск (`ops.archiver.failed_count`, drill 08).
- У проді ціль — S3/GCS/сервер бекапів через pgBackRest, WAL-G або Barman, **не** `cp`. Вони додають стиснення, шифрування, retention, паралелізм і верифікацію. Вивчіть один з них наступним.

## Кроки

1. **Базовий бекап** (тут із репліки, щоб не навантажувати primary):
   ```sh
   pg_basebackup -h pg2 -p 5432 -U replicator -D /backup/base-1 -Fp -X stream -c fast -P
   ```
   `-X stream` включає WAL, потрібний для узгодженості копії. `-c fast` примусово робить негайний checkpoint.
2. Продовжуйте архівувати. `select * from ops.archiver;` має показувати, що `failed_count` не росте.
3. **Запишіть момент перед помилкою.** У реальному житті це найважча частина: логи, події застосунку, `pg_waldump`.
   Можна також цілитись у **id транзакції** (`recovery_target_xid`), **іменовану точку відновлення** (`select pg_create_restore_point('before_release')`) або **LSN**.
4. **Відновлюйте на окремий сервер**, ніколи поверх живого (`drills/10-backup-and-pitr/restore.sh`):
   ```
   <data dir> = базовий бекап
   touch recovery.signal
   postgresql.auto.conf:
       restore_command = 'cp /archive/%f %p'
       recovery_target_time = '2026-10-18 12:30:00+00'
       recovery_target_action = 'promote'
   start postgres
   ```
   Дивіться в його лог: `starting point-in-time recovery to ...`, `restored log file ... from archive`, `recovery stopping before commit of transaction ...`, `archive recovery complete`.
5. **Витягніть лише потрібне** (`pg_dump -t core.transactions`) і завантажте в прод. Не перемикайте прод на відновлену копію, якщо не мусите.

## Що йде не так

| Проблема | Чому |
|---|---|
| `recovery ended before configured recovery target was reached` | в архіві бракує WAL до цілі (прогалина або архівація падала) |
| Відновлюється на надто пізній/ранній час | цільовий час — це момент за годинником: перевірте часові пояси і чи DROP був до чи після вашої позначки |
| `could not open file ... No such file` для сегмента WAL | хибний шлях у `restore_command` або сегмент видалила job з retention |
| Відновлення повільне | програвання WAL однопоточне: день інтенсивного WAL може зайняти години. Робіть базові бекапи частіше |
| Відновлений сервер не стартує | хибні права (`chmod 700` на data dir, власник `postgres`) або застарілий `postmaster.pid` |
| Після PITR у вас новий timeline | очікувано: відновлений сервер починає новий timeline; він більше не може йти за старим primary |

## Бекап, який ви не відновлювали, — це надія

Поставте **тест відновлення** за розкладом: відновіть останній бекап на тимчасову машину, зробіть підрахунок рядків і кілька запитів, запишіть час.
Цей час — ваш справжній RTO. Drill 10 робить саме це в лабораторії.

## Логічні бекапи (`pg_dump`) проти фізичних

| | Фізичний (`pg_basebackup`, pgBackRest) | Логічний (`pg_dump`) |
|---|---|---|
| Швидкість відновлення | швидка (копіювання файлів) | повільна (перебудова кожного індексу) |
| PITR | **так** (з WAL) | ні |
| Гранулярність | весь кластер | база/таблиця |
| Між версіями | ні | так |
| Використовувати для | аварійного відновлення | перенесення даних, витягання однієї таблиці, оновлень |
