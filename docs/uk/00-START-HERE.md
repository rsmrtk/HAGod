# Почніть тут: план

Ви казали, що найважче в роботі — це **PostgreSQL з Patroni** і **Redis із Sentinel**. Знати команди замало; важливо, що ви робите о 3-й ночі, коли одне з них горить. Тому ця лабораторія тренує те, що важко отримати деінде: **залишатися спокійним і діяти правильно, поки воно ламається.**

## Метод (однаковий для кожного drill)

1. **Передбачте.** Перш ніж щось натискати, запишіть (хоч одним рядком), що, на вашу думку, станеться і скільки це займе. Хибний прогноз — найцінніше, що може дати лабораторія: він точно показує, чого ви ще не розумієте.
2. **Зламайте.** `make drill-NN`. Скрипт скаже, що саме зробив, і запустить годинник.
3. **Спостерігайте.** Дивіться `make watch`. Потім дослідіть власними командами (вони є в README кожного drill). **Не** користуйтесь `make heal`.
4. **Полагодьте.** Поверніть систему до життя вручну. README drill описує, як виглядає добре виправлення.
5. **Виміряйте.** `make verify-NN` друкує цифри: скільки це тривало, скільки записів втрачено.
6. **Напишіть runbook.** Достатньо трьох рядків: симптом, як підтвердити, що робити. Шаблон — `docs/07-runbook-template.md`.
7. **Занесіть у журнал** `docs/08-progress.md` (ваше табло).

Кожен drill робіть **двічі**: перший раз із README, другий — без нього. Лише другий раз вважається засвоєним.

## Налаштування (один раз)

```sh
cd ~/s/hub/HAgod
make up && make seed && make writer-start
make obs-up          # необов'язково, але варто: Grafana http://localhost:3300 (логін admin / admin)
```

Тримайте два термінали: в одному `make watch`, в іншому ваші команди (`make shell` дає `psql`, `patronictl`, `redis-cli`).

Перед кожним drill перевіряйте, що все здорове: `make status` має показувати 1 primary і 2 streaming-репліки, 1 Redis master із 2 репліками, `quorum check: OK`. Якщо ні — `make heal`.

## Правила, які змушують це працювати

- **Ніколи не пропускайте крок 1.** Спершу передбачайте.
- **Не користуйтесь `make heal`, поки практикуєтесь.** Він для проміжків між drill. Ручне лагодження — і є навичка.
- **Записуйте цифри.** «Failover тривав 25 с» — це знання; «було швидко» — ні.
- **Спочатку ламайте щось одне, потім комбінуйте.**
- **Читайте логи** (`docker logs pg1`, `docker logs sentinel1`). У проді у вас здебільшого будуть логи й метрики, а не дебагер.

## Чим це відрізняється від вашого банку (і що там спитати)

Ця лабораторія використовує **etcd** для Patroni і **HAProxy** спереду. У вашому банку можуть бути Consul, ZooKeeper або вбудований Raft Patroni, а замість HAProxy — `vip-manager` чи `pgbouncer`/`pgpool`. Уроки переносяться, але перевірте:

- Який DCS ми використовуємо, скільки вузлів і на яких хостах? (drill 03)
- Чи реплікація синхронна? Strict? (drill 05)
- Чому дорівнюють `ttl`, `loop_wait`, `retry_timeout`, `maximum_lag_on_failover`? (`patronictl show-config`)
- Куди йдуть бекапи, як часто їх відновлюють для перевірки, і яка процедура PITR? (drill 10)
- Як клієнти Redis знаходять master: Sentinel-aware клієнт чи проксі? (drills 11, 13)
- Чи Sentinel'и на окремих хостах від Redis? Чи встановлено `min-replicas-to-write`? Персистентність AOF чи RDB? (drills 12, 13)

Принесіть ці питання на роботу: саме їх ставить senior-рев'юер.
