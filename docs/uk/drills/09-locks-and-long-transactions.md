# Drill 09: Блокування і забута транзакція

**Мета.** Знайти блокувальника, а не жертв, і безпечно його зупинити.

## Історія
Застосунок «висне». З'єднання ростуть. CPU простоює. Хтось десь має відкриту транзакцію.

## Спостерігайте: команди, які варто спробувати самому
```sql
select * from ops.blocked;                      -- хто на кого чекає і як довго
select * from ops.activity;                     -- зверніть увагу на state = 'idle in transaction'
select pid, state, now()-xact_start as xact_age, query from pg_stat_activity where state='idle in transaction';
select * from pg_locks where not granted;       -- сира таблиця блокувань
```

## Що ви маєте побачити
Сесія A тримає блокування рядка у стані `idle in transaction`; B чекає на цей рядок; C чекає на блокування таблиці позаду них. `ops.blocked` показує `blocking_pid`, що вказує на A (а C також чекає на B). Завершення A звільняє всіх.

## Зрозумійте
Транзакція, що відкрита й простоює, тримає свої блокування та snapshot, доки не завершиться. Усе, що потребує конфліктного блокування, стає за нею в чергу, і **усе стає в чергу за чергою** (очікуване блокування таблиці блокує й нових читачів). Убивство найдовшого *очікувача* нічого не змінює; треба прибрати **блокувальника в корені ланцюга**.

Стара відкрита транзакція також не дає VACUUM прибирати мертві рядки новіші за неї, тож таблиці роздуваються, поки вона існує.

## Виправлення
```sql
select pg_terminate_backend(<blocking_pid>);     -- кореневий блокувальник; pg_cancel_backend скасовує лише запит, що виконується, а не транзакцію, що простоює
```
Запобігайте: `idle_in_transaction_session_timeout` (напр. 60 с), `lock_timeout`, і виправте застосунок (завжди commit/rollback, короткі транзакції). У Patroni виставляйте їх через `patronictl edit-config`.

### Відповіді (читайте після спроби)
1. A (транзакція, що простоює). B і C лише чекали.
2. A простоює: нема запиту, що виконується, щоб його скасувати; треба завершити саму відкриту транзакцію, тож ви термінуєте backend.
3. VACUUM не може прибрати dead tuples новіші за її snapshot (bloat), на репліках можуть виникати конфлікти запитів, і вона може стримувати `xmin` для всього кластера.
