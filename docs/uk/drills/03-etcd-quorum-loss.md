# Drill 03: Втратити etcd

**Мета.** Зрозуміти, що Patroni залежить від свого DCS, і що відбувається, коли DCS зникає.

## Історія
Аварія стійки знімає два з трьох хостів etcd. Postgres чудово працює на всіх трьох хостах баз даних. Що бачить застосунок?

## Спершу передбачте (запишіть)
- Чи primary продовжує обслуговувати записи?
- Чи промотять якусь репліку?
- Чи втрачено дані?

## Запуск
```sh
make drill-03        # зупиняє etcd2 і etcd3
make verify-03       # показує стан, потім відновлює etcd
```

Тримайте `make watch` відкритим у другому терміналі.

## Спостерігайте: команди, які варто спробувати самому
```sh
docker exec etcd1 etcdctl endpoint health --cluster     # unhealthy: нема кворуму
patronictl list                                          # висне або видає помилку: він читає з etcd
for p in 8101 8102 8103; do curl -s localhost:$p/patroni | jq -c '{role,state}'; done   # кожен вузол каже: replica
docker logs pg1 2>&1 | grep -iE "DCS|demot|failsafe" | tail    # причина словами Patroni
```

## Що ви маєте побачити
**Усі три вузли стають read-only репліками приблизно за один `ttl`**, і записи падають. Процеси Postgres досі працюють, дані не втрачено. Коли etcd повертається, попередній primary знову бере лок, і записи відновлюються, зазвичай без нового timeline.

## Зрозумійте
Правило Patroni: *primary має довести, що досі володіє локом.* Без etcd він не може, тож демотить себе, щоб уникнути ймовірності появи другого primary з іншого боку. Ціна: **аварія etcd — це аварія бази даних**. Тому etcd мусить працювати на окремих надійних хостах і моніторитись першим.

Patroni має `failsafe_mode`: якщо всі учасники ще можуть напряму досягти одне одного, primary може продовжувати працювати без DCS. Спробуйте: `patronictl edit-config --force -s failsafe_mode=true`, потім повторіть drill і порівняйте.

## Виправлення
Відновіть кворум etcd (`docker start etcd2 etcd3`). Потім переконайтесь, що є один лідер, а репліки стрімлять. Подумайте, що б ви робили в проді, якби дані etcd були втрачені (відновити зі snapshot etcd: `etcdctl snapshot save/restore`).

---

### Відповіді (читайте після спроби)
1. Щоб гарантувати, що ніколи не буде більше одного primary: нема лока — нема записів.
2. Primary продовжує працювати, поки може напряму спілкуватись з іншими учасниками Patroni. Ризик: якщо справжня причина — partition, ви покладаєтесь на ці прямі зв'язки для рішення, що слабше за консенсусне сховище.
3. З 3: одного. З 5: двох. З 2: жодного (і 2 гірше за 1: будь-яка відмова втрачає кворум). Завжди використовуйте непарне число.
