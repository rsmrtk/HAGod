# Drill 15: Повільна команда викликає failover

**Мета.** Дізнатись, що здоровий, але зайнятий Redis можуть оголосити мертвим.

## Історія
Хтось запускає на master дорогу команду. З машиною нічого не так. Через кілька секунд стається failover.

## Спершу передбачте (запишіть)
- Чи Sentinel зробить failover? Чи процес впав?
- Що зробить старий master, коли команда завершиться?

## Запуск
```sh
make drill-15
make verify-15
```

Тримайте `make watch` відкритим у другому терміналі.

## Спостерігайте: команди, які варто спробувати самому
```sh
docker logs sentinel1 2>&1 | grep -E "sdown|odown|switch-master"
redis-cli -h <old master> slowlog get 3
redis-cli -h <old master> latency latest
```

## Що ви маєте побачити
Через ~**5-7 с** sentinel'и логують `+sdown`, `+odown` і `+switch-master`: **failover стався для процесу, який ніколи не падав.** Старий master, коли прокидається, демотується до репліки. Slow log записує 8-секундну команду.

## Зрозумійте
Redis виконує команди в одному потоці. Поки він виконує одну повільну команду, він не відповідає нікому, зокрема на `PING` від Sentinel. Після `down-after-milliseconds` (5 с) sentinel'и не можуть відрізнити «зайнятий» від «мертвий», тож роблять failover. Реальні тригери: `KEYS *`, `SMEMBERS` або `HGETALL` величезного ключа, `DEL` величезного ключа (використовуйте `UNLINK`), повільний Lua-скрипт, `SAVE` або зависання машини.

## Виправлення
Усуньте причину: використовуйте `SCAN`, `UNLINK`, `SSCAN`/`HSCAN`; тримайте скрипти короткими; ставте alert на `slowlog`; підлаштуйте `down-after-milliseconds` довшим за вашу найповільнішу легітимну команду; обмежте небезпечні команди через ACL.

## Ваш runbook
Напишіть три рядки, перш ніж читати відповіді: **симптом → як підтвердити → що робити.** (Шаблон: `docs/07-runbook-template.md`.)

## Питання
1. Як би ви запобігли такому класу інцидентів?
2. Що ви виграєте і втрачаєте, виставивши `down-after-milliseconds` у 20 с?
3. Який alert попередив би вас до того, як це станеться?

---

### Відповіді (читайте після спроби)
1. Заборонити `KEYS`/`FLUSH*` для користувачів застосунку (ACL), використовувати інкрементальні команди, `UNLINK` і стежити за slowlog.
2. Менше хибних failover'ів, але справжня аварія виявляється 20 с+ (порівняйте drill 11).
3. Зростаючий `slowlog_length`, події `latency` та `instantaneous_ops_per_sec`, що падає до 0, поки процес живий.
