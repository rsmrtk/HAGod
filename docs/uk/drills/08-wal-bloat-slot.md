# Drill 08: pg_wal заповнює диск

**Мета.** Розпізнати дві класичні причини переповненого каталогу WAL: осиротілий replication slot і `archive_command`, що падає.

## Історія
2-га ночі: диск primary на 95% і росте. Записи застосунку ще працюють. Як знайти причину, поки Postgres не зупинився?

```sh
select * from ops.slots;            -- неактивний slot з великим wal_retained
select * from ops.archiver;         -- failed_count росте? last_failed_wal?
docker exec pg1 du -sh /var/lib/postgresql/data/pgdata/pg_wal
docker exec pg1 ls /var/lib/postgresql/data/pgdata/pg_wal/archive_status | grep -c ready
df -h                                -- на справжньому хості
```

## Що ви маєте побачити
`orphan_slot` показує `active = f` із **гігабайтами** в `wal_retained`, а `pg_wal` росте в кілька разів понад свій звичайний розмір. Patroni його **не** видаляє (він керує лише slots для своїх учасників). Видалення звільняє WAL при наступному checkpoint.

## Зрозумійте
Replication slot змушує primary тримати кожен сегмент WAL, якого споживач slot ще не підтвердив, **вічно**. Якщо споживач мертвий (видалена репліка, зупинений інструмент logical decoding, забутий тест), WAL ніколи не зникне. Інша класична причина — `archive_command`, що падає: сегменти чекають на архівацію, файли `.ready` накопичуються, і `pg_wal` пухне (це траплялось цій лабораторії, поки її будували: баг `cmp ... && mv`; `ops.archiver.failed_count` його показав).

`max_slot_wal_keep_size` обмежує, скільки slot може утримувати: понад це slot інвалідується замість того, щоб заповнити диск (тоді його споживача треба перебудувати).

## Виправлення
```sql
select pg_drop_replication_slot('orphan_slot');
checkpoint;
```
Потім переконайтесь, що моніторинг сповіщає про неактивні slots і про `failed_count` (`obs/alerts.yml` має обидва). Виставте `max_slot_wal_keep_size` у те, що ваш диск витримає.

### Відповіді (читайте після спроби)
1. Patroni керує лише slots, які сам створює для учасників кластера (і тими, що ви оголосили в його конфігу `slots:`). Slot, створений вручну, поза його зоною.
2. `max_slot_wal_keep_size`. Коли його перевищено, slot позначається втраченим, і його споживач (репліка чи CDC-інструмент) більше не може продовжити; його треба перебудувати: захист диска primary важливіший за збереження застарілого споживача.
3. `pg_replication_slots_active == 0` протягом 1 хвилини, і slot, що утримує понад N ГБ (N = безпечна частка вільного диска), плюс `increase(pg_stat_archiver_failed_count[2m]) > 0`.
