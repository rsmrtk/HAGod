# Drill 13: Split brain у Redis

**Мета.** Побачити, як розділення мережі створює два master і губить підтверджені записи, і як `min-replicas-to-write` це обмежує.

## Історія
Мережа між Redis master і рештою ламається, але деякі клієнти досі досягають старого master. Обидві сторони думають, що праві.

## Спершу передбачте (запишіть)
- Скільки записів, прийнятих старим master, виживе?
- Як змінює це захист?

## Запуск
```sh
./drills/13-redis-split-brain/break.sh plain       ; make verify-13
make heal
./drills/13-redis-split-brain/break.sh protected   ; make verify-13
```

Тримайте `make watch` відкритим у другому терміналі.

## Спостерігайте: команди, які варто спробувати самому
```sh
redis-cli -h <old master> role                    # досі каже master
redis-cli -h sentinel1 -p 26379 sentinel get-master-addr-by-name mymaster   # каже новий
docker exec tools tail /tmp/stale-writes.log      # застарілий клієнт: OK або помилки NOREPLICAS
```

## Що ви маєте побачити
Plain: **~130 записів** застарілого клієнта були прийняті ізольованим master і **0 вижило** після відновлення зв'язку. Protected (`min-replicas-to-write 1`, `min-replicas-max-lag 5`): master відмовляв у записах приблизно через 5 с, прийнято лише **~25**, решта отримала `NOREPLICAS`. Все одно не нуль: реплікація асинхронна.

## Зрозумійте
Коли partition зникає, старий master переналаштовується як репліка нового master і **виконує повний ресинк, відкидаючи все, що прийняв, поки був ізольований**. Злиття нема. `min-replicas-to-write` змушує ізольований master перестати приймати записи, коли він не отримував ack від жодної репліки `min-replicas-max-lag` секунд: це звужує вікно втрат, але робить master недоступним для запису, коли його репліки впали.

## Виправлення
Визначте політику: доступність (приймати записи, ризикувати втратою) чи безпека (відмовляти в записах). Змусьте клієнтів використовувати Sentinel-aware з'єднання, що оновлюють адресу master.

## Ваш runbook
Напишіть три рядки, перш ніж читати відповіді: **симптом → як підтвердити → що робити.** (Шаблон: `docs/07-runbook-template.md`.)

## Питання
1. Які клієнти в реальному житті продовжують писати у старий master?
2. Який компроміс у `min-replicas-to-write`?
3. Чи можна злити втрачені записи назад?

---

### Відповіді (читайте після спроби)
1. Пули з'єднань, що ніколи не оновлюються, клієнти із жорстко прописаною адресою, адреси, закешовані в DNS, довгоживучі з'єднання в batch-завданнях.
2. Менше втрат, але master стає недоступним для запису щоразу, коли репліки відстають або впали.
3. Ні. Зміни старого master перезаписуються ресинком; потрібне було б узгодження на рівні застосунку (ідемпотентні записи, outbox або event sourcing).
