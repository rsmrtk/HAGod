# Drill 05: Async проти синхронної реплікації

**Мета.** Виміряти у втрачених записах, чого справді коштує асинхронна реплікація і чого натомість коштує строгий синхронний режим.

## Історія
Бізнес питає: «чи можемо ми коли-небудь втратити платіж, який підтверджено клієнту?» Відповісти треба цифрами, а не думками.

## Спершу передбачте (запишіть)
- Async: скільки підтверджених записів буде бракувати потім?
- Strict: скільки, і що натомість переживає застосунок?

## Запуск
```sh
./drills/05-async-vs-sync/break.sh async     # потім make verify-05
make heal
./drills/05-async-vs-sync/break.sh strict    # потім make verify-05
```
Скрипт відрізає репліки, дає застосунку писати 20 с, вбиває primary і знову підключає репліки.

Тримайте `make watch` відкритим у другому терміналі.

## Спостерігайте: команди, які варто спробувати самому
```sh
patronictl list                       # Role: Sync Standby у strict-режимі
patronictl show-config | grep -i sync
select application_name, state, sync_state from pg_stat_replication;     # sync / async / potential
show synchronous_standby_names;
make report
```

## Що ви маєте побачити
**Async: близько 100 підтверджених записів втрачено** (усе записане за 20 с, коли репліки не могли отримувати WAL). **Strict: 0 втрачено**, але під час розриву записи **блокуються** (жоден commit не завершується), а потім падають: доступність обміняно на безпеку. Після failover кластер повертається до норми.

## Зрозумійте
Асинхронна реплікація означає, що primary підтверджує commit, щойно він на **його власному** диску. Якщо він помирає раніше, ніж репліка отримала WAL, цей commit зникає. Синхронна реплікація чекає на standby. У Patroni три рівні: **async** (за замовчуванням); **`synchronous_mode`** (віддає перевагу sync standby, але якщо жодного немає, тихо повертається до async, щоб лишатись доступним: тож може все одно втратити дані); і **`synchronous_mode_strict`** (ніколи не підтверджує без standby: нема втрат, але записи зупиняються, коли standby зникає).

Лише **синхронний standby** може бути промотований у sync-режимі, і саме це робить обіцянку «без втрат» дійсною.

## Виправлення
`make heal` скидає sync-налаштування. У реальному житті узгодьте політику з бізнесом, запишіть її в runbook і моніторьте `sync_state`.

## Ваш runbook
Напишіть три рядки, перш ніж читати відповіді: **симптом → як підтвердити → що робити.** (Шаблон: `docs/07-runbook-template.md`.)

## Питання
1. Що гірше для банку: кілька секунд невдалих записів чи кілька втрачених підтверджених платежів? Хто вирішує?
2. Що робить нестрогий `synchronous_mode`, коли standby зникає, і чи гарантує він відсутність втрат?
3. На що б ви ставили alert?

---

### Відповіді (читайте після спроби)
1. Зазвичай гірші втрачені підтверджені платежі; це бізнесове рішення щодо ризику, зафіксоване письмово. Багато банків обирають strict або `remote_apply` для основних ledger'ів і приймають ціну в доступності.
2. Він повертається до async, щоб сервіс лишався доступним, тож **не** гарантує нульових втрат у цьому вікні. Лише strict гарантує.
3. Кількість sync standby < 1, `sync_state` не `sync`, lag реплікації та відсутні рядки в `pg_stat_replication`.
