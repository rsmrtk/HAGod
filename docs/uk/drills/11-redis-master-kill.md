# Drill 11: Вбити Redis master

**Мета.** Побачити, як Sentinel робить failover, і виміряти його.

## Історія
Хост Redis master помирає. Від нього залежать сесії та кеші.

## Спершу передбачте (запишіть)
- Яку репліку промотять? Скільки це триватиме?
- Чи старий master повернеться як master?

## Запуск
```sh
make drill-11
make verify-11
```

Тримайте `make watch` відкритим у другому терміналі.

## Спостерігайте: команди, які варто спробувати самому
```sh
docker logs sentinel1 2>&1 | grep -E "sdown|odown|elected|selected-slave|promoted|switch-master"
redis-cli -h sentinel1 -p 26379 sentinel get-master-addr-by-name mymaster
redis-cli -h <node> role
make report
```

## Що ви маєте побачити
Новий master з'являється через **~6 с** (5 с `down-after-milliseconds` + вибори, ~1 с). Застосунок бачить ~6 с без записів у Redis. Перезапущений старий master приєднується як **репліка** (entrypoint питає Sentinel, хто master).

## Зрозумійте
Кожен sentinel пінгує master. Після `down-after-milliseconds` без валідної відповіді він ставить `+sdown` (суб'єктивно недоступний). Коли `quorum` (2) sentinel'ів погоджуються, це `+odown`. Потім sentinel'и **обирають серед себе** лідера failover (потрібна більшість: 2 з 3), який вибирає найкращу репліку (пріоритет, offset, run id), надсилає `REPLICAOF NO ONE` і повідомляє іншим (`+switch-master`). Реплікація асинхронна, тож останні записи перед аварією можуть бути втрачені.

## Виправлення
Перезапустіть мертвий вузол і переконайтесь, що він репліка нового master (`ROLE`). Якщо він колись стартує сам як master (застарілий конфіг), Sentinel його демотить, але записи, які він прийняв у той момент, втрачаються.

## Ваш runbook
Напишіть три рядки, перш ніж читати відповіді: **симптом → як підтвердити → що робити.** (Шаблон: `docs/07-runbook-template.md`.)

## Питання
1. Які записи можуть бути втрачені і чи можна зменшити їх кількість?
2. Чому перезапущений старий master не повернувся як master?
3. Як клієнти знаходять новий master?

---

### Відповіді (читайте після спроби)
1. Записи, підтверджені master, але ще не отримані репліками. Менше: `min-replicas-to-write` плюс `WAIT` для важливих записів, але в async-реплікації нуля нема.
2. Наш entrypoint спершу питає Sentinel, і Sentinel усе одно переналаштував би його як репліку нового master. Вузол, що повертається як master зі старими даними, був би демотований, а його дані відкинуті.
3. Питаючи Sentinel (`GET-MASTER-ADDR-BY-NAME`) при кожному перепідключенні; Sentinel-aware бібліотека клієнта робить це автоматично. Проксі нема.
