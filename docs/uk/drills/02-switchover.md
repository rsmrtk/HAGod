# Drill 02: Плановий switchover

**Мета.** Перенести primary навмисно й порівняти з аварією.

## Історія
Сьогодні вночі треба запатчити хост primary. Як перенести записи з мінімальною шкодою?

## Спершу передбачте (запишіть)
- Скільки часу порівняно з drill 01? Чому?
- Чи помітить застосунок взагалі?

## Запуск
```sh
make drill-02
make verify-02
```

Тримайте `make watch` відкритим у другому терміналі.

## Спостерігайте: команди, які варто спробувати самому
```sh
patronictl list -W
docker logs pg1 2>&1 | grep -E "demot|release|promot|switchover" | tail
make report
```

## Що ви маєте побачити
Близько **3 с**, щоб команда завершилась, і **~4 с** невдалих записів з погляду застосунку; `LOST WRITES: 0` тут гарантовано. Порівняйте з ~25 с для аварії.

## Зрозумійте
Switchover — **кооперативний**. Patroni спершу змушує старий primary перестати приймати записи й чекає, поки обрана репліка повністю наздожене, потім навмисно **віддає** ключ лідера. Кандидат одразу його забирає, ніхто не чекає на TTL, і дані не можуть бути втрачені, бо репліка мала все.

## Виправлення
Виправляти нічого. Спробуйте варіанти: оберіть кандидата (`--candidate pg3`), заплануйте (`--scheduled "2026-10-20T03:00"`), скасуйте запланований (`patronictl flush hagod switchover`).

## Ваш runbook
Напишіть три рядки, перш ніж читати відповіді: **симптом → як підтвердити → що робити.** (Шаблон: `docs/07-runbook-template.md`.)

## Питання
1. Чому switchover набагато швидший і безпечніший за аварію?
2. Коли б ви використали `failover` замість нього?
3. Що треба перевірити перед будь-яким switchover?

---

### Відповіді (читайте після спроби)
1. Старий primary сам передає лок, а репліка повністю наздогнала, тож нема очікування TTL і нема втрат.
2. Лише коли **нема здорового лідера**, щоб передати (primary зник, і ніхто автоматично не перебрав).
3. Що всі репліки `streaming` з lag 0 (`patronictl list`) і що кандидат не `nofailover`. Завжди читайте запит підтвердження (не використовуйте `--force` у проді).
