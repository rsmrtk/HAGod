# Drill 04: Ізолювати primary від мережі

**Мета.** Небезпечна відмова: вузол живий, але недосяжний.

## Історія
Відмовляє комутатор. Primary працює, абсолютно здоровий, і його клієнти зі старого боку досі з ним говорять. Решта кластера його не бачить. Що не дає виникнути двом primary?

## Спершу передбачте (запишіть)
- Чи ізольований вузол продовжує приймати записи? Як довго?
- Що робить решта кластера і як швидко?

## Запуск
```sh
make drill-04
make verify-04
```

Тримайте `make watch` відкритим у другому терміналі.

## Спостерігайте: команди, які варто спробувати самому
```sh
docker logs pgN 2>&1 | tail -20            # на ізольованому вузлі: що вирішив Patroni, коли втратив etcd
docker exec pgN ps aux | grep postgres      # чи Postgres досі працює там?
patronictl list -W                          # з контейнера tools: погляд тих, що вціліли
```

## Що ви маєте побачити
Patroni ізольованого вузла не може поновити свій лок, тож **повністю зупиняє Postgres** (не лише read-only). Два інших обирають новий primary приблизно через `ttl`, тож застосунок бачить близько **20-30 с без записів**. Після відновлення зв'язку старий primary повертається; `pg_rewind` або повторне клонування робить його репліку. Записи, надіслані на ізольований вузол за секунди до його зупинки, можуть бути втрачені.

## Зрозумійте
Зупинка — це і є весь захист: Patroni **відгороджує себе сам (fencing)**. Вузол, що не може досягти DCS, мусить перестати бути primary *до того*, як будь-який інший вузол ним стане. Інший бік промотить лише після TTL, який довший за час, потрібний ізольованому primary, щоб зупинитись. Саме тому важить `loop_wait + 2*retry_timeout <= ttl`: воно гарантує, що fencing закінчиться раніше за вибори.

## Виправлення
Відновіть мережу, дивіться, як вузол повертається (`patronictl list`). Знайдіть у його логу, чи він використав `pg_rewind`, чи повний basebackup, і чому.

Напишіть три рядки, перш ніж читати відповіді: **симптом → як підтвердити → що робити.** (Шаблон: `docs/07-runbook-template.md`.)

## Питання
1. Що не дало ізольованому primary вічно приймати записи?
2. Як ще захиститись від primary, якого сам Patroni не може зупинити (завислий хост)?
3. Які записи можуть бути втрачені і як це дізнатись?

---

### Відповіді (читайте після спроби)
1. Самовідгородження Patroni: нема поновлення лока, тож він демотить/зупиняється в межах таймауту, до завершення виборів.
2. **Watchdog**: Patroni може озброїти апаратний/програмний watchdog, що перезавантажує хост, якщо сам Patroni перестає відповідати. Налаштуйте `watchdog:` у Patroni і пристрій `softdog`/апаратний на хості.
3. Записи, підтверджені старим primary після останнього WAL, відправленого на репліку. Порівняйте з логами застосунку й рядком `LOST WRITES`.
