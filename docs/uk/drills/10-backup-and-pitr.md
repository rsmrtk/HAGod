# Drill 10: Бекап і point-in-time recovery

**Мета.** Відновити видалену таблицю на момент перед помилкою, не зупиняючи прод.

## Історія
Хтось видаляє `core.transactions` у проді. DROP миттєво реплікується на кожну репліку. Як повернути дані і наскільки швидко?

## Спершу передбачте (запишіть)
- Чи допоможуть репліки? (Ні: запишіть чому.)
- Скільки рядків має мати відновлена таблиця?
- Скільки триватиме відновлення?

## Запуск
```sh
make drill-10                                  # бекап, ще записи, потім DROP
./drills/10-backup-and-pitr/restore.sh         # PITR у тимчасовий сервер з назвою 'pitr'
make verify-10                                 # порівняти кількість рядків; за бажанням скопіювати таблицю назад
```

Тримайте `make watch` відкритим у другому терміналі.

## Спостерігайте: команди, які варто спробувати самому
```sh
select to_regclass('core.transactions');                 -- NULL: зникла
docker exec tools ls /backup /archive | tail             # базовий бекап і заархівований WAL
docker logs pitr 2>&1 | grep -E "recovery|restored log file|stopping"   # PITR у процесі
docker exec pitr psql -h localhost -U postgres -d bank -c "select count(*) from core.transactions"
```

## Що ви маєте побачити
Відновлений сервер зупиняється **просто перед DROP** і має рівно ту кількість рядків, що була записана в останній добрий момент. Ви копіюєте таблицю назад через `pg_dump | psql`, і прод ніколи не зупинявся. Відновлення тут зайняло секунди, бо даних мало: **виміряйте його й екстраполюйте на ваш розмір**; це ваш справжній RTO.

## Зрозумійте
PITR = фізичний базовий бекап + безперервний WAL-архів. Postgres відновлює файли, потім **програє заархівований WAL** (`restore_command`) до `recovery_target_time`, потім промотиться. Досяжний RPO — наскільки свіжий останній заархівований WAL (тут `archive_timeout = 60` с); RTO — час копіювання + час replay.

Відкладена репліка (`recovery_min_apply_delay`) — ще один захист від людської помилки, але вона не замінює бекапи.

## Виправлення
Відновлюйте на **окремий** сервер, витягніть лише пошкоджений об'єкт, поверніть його. Перемикання проду на відновлену копію — крайній засіб.

Напишіть три рядки, перш ніж читати відповіді: **симптом → як підтвердити → що робити.** (Шаблон: `docs/07-runbook-template.md`.)

## Питання
1. Який ваш справжній RPO для такої помилки?
2. Скільки тривало відновлення? Екстраполюйте на розмір вашого проду.
3. Що має містити архів? Що, якщо бракує одного сегмента?
4. Як би ви тестували відновлення автоматично?

### Відповіді (читайте після спроби)
1. Час між останнім заархівованим WAL і помилкою, плюс те, як швидко ви **помітите** і знайдете правильний цільовий час. Часто домінує саме помічення.
2. Час копіювання базового бекапу (розмір / пропускна здатність) + час replay WAL (однопотоковий, може бути довгим за завантажений день). Міряйте на відновленні реального розміру.
3. Кожен сегмент від початку базового бекапу до цілі. Прогалина зупиняє відновлення на прогалині (`recovery ended before configured recovery target`).
4. Запланована job відновлює найновіший бекап на тимчасовий хост, запускає sanity-запити, записує тривалість, сповіщає про збій.
